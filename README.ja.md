# AWS Bill Explained

[English](README.md) · [日本語](README.ja.md)

AWS の請求書で回っているメーターは3つだけ。3つ覚えれば、料金ページは勉強ではなく参照になる。

AWS は料金をサービスごとに書いている。だから新しいサービスを触るたびに、課金の仕組みを覚え直す羽目になる。実際はそうじゃない。メーターは3種類しかなく、各サービスはそのどれを持っているかが違うだけだ。

| メーター            | 判定する問い                         | 数えているもの                                           |
| ------------------- | ------------------------------------ | -------------------------------------------------------- |
| **Time** (稼働時間) | それは「存在している」か？           | 量 × 時間                                                |
| **Bytes** (バイト)  | ギガバイトを数えているものがあるか？ | 境界を出ていく転送と、経路上の装置がかける処理 GB の両方 |
| **Units** (個数)    | 離散的な何かをいくつ頼んだか？       | リクエスト、トークン、ページ、文字、宛先、ペイロード片   |

2本目を Egress ではなく **Bytes** と呼んでいるのは意図的。「入ってくる分は無料」は**データ転送に固有のルール**であって、メーターの性質ではない。CloudWatch の取り込み、Firehose の受け口、NAT Gateway の処理は、いずれも方向に関係なく GB を数える。

3本目を Calls ではなく **Units** と呼んでいるのも同じ理由。「API を呼んだ回数。サイズも方向も関係ない」という定義は、課金の形ではなく実装のひとつを説明していた。Units に分類されるサービスの多くが、その定義に当てはまらない。SQS は 1 MiB の呼び出しを 16 リクエストとして課金し、Bedrock はトークン、Textract はページ、SES は宛先を数える。共通しているのは**離散的な何かが数えられる**ことで、リクエストはその一番よくある実例にすぎない。

このサイトは AWS の各サービスをこの3つに分類し、そのサービスで一番よく間違えられる点を説明し、自分の請求書で探すための usage type を示す。

## 原則

- **データセットに金額を書かない。** レートは動くしリージョンでも違う。どのメーターが回るかは動かない。本文に金額が混じったレコードは `Service` のコンストラクタが拒否する
- **すべての主張に AWS の出典と確認日を持たせる。** 出典が無いレコード、AWS 以外のドメインを引いたレコードは `Service` のコンストラクタが拒否する
- **色が付いていれば課金、グレーなら無料。** ただし色だけには載せない。グレースケールでもスクリーンリーダーでも成立する必要がある
- **結論のモデルを先に渡す。** 各ページは1文から始めて、その後に根拠を置く

AWS 公式とは無関係の非公式な解説。

## コマンド

```bash
npm install
npm run dev         # ローカル開発サーバ
npm run test        # ドメイン・図形計算・i18n・カタログのテスト
npm run test:smoke  # ビルド済みページをブラウザで開く (先に npm run build が要る)
npm run check       # lint + 型 + テスト + ビルド + スモーク (CI と同じ)
npm run build       # dist/ への静的ビルド
```

`npm run test:smoke` は `scripts/serve-dist.mjs` 経由で `dist/` を配信し、`public/_headers` の内容を実際に適用する。これは意図的で、`astro preview` はそのヘッダを無視するし、このテストが最後に捕まえた不具合はページではなくヘッダ側にあった。

## 構成

```text
src/
  domain/          純粋な TypeScript。Astro もロケールも知らない
    meter.ts       MeterSet 値オブジェクト
    service-slug.ts  ServiceSlug 値オブジェクト。自分で自分を検証する同一性
    service.ts     Service エンティティ。コンストラクタが編集ルールを強制する
    catalogue.ts   Catalogue 集約。サービス横断のクエリは全部ここ
  infrastructure/
    service-repository.ts   調査 JSON に対する腐敗防止層
  lib/
    diagram-layout.ts   SVG の幾何計算。テスト可能にするため切り出した
  data/services/   カテゴリごとの JSON。調査済みデータセット
  content/topics/  長文の深掘り。<lang>/<slug>.mdx
  components/      表示層。SVG の図解コンポーネントを含む
  pages/           ルート。英語は接頭辞なし、他ロケールは /<lang>/ 配下
scripts/
  check-build.mjs     型チェッカーに見えないものへのビルド後ガード
  check-sources.mjs   引用した AWS の URL が生きているか検証
  merge-services.mjs  調査バッチをカテゴリ別データセットに取り込む
```

サービスページはカタログから生成される。**サービスの追加はデータ変更であって、コード変更ではない。**

### なぜドメイン層があるのか

データセットは独立した複数の調査パスから組み上がっていて、命名が割れる (`amazon-s3` と `s3`)。ときどき誰も見たことのないメーター文字列も混じる。`ServiceSlug` は同一性を間違えようがなくする — その値を持つ唯一の方法がコンストラクタを通ることだから。そしてリポジトリは未知のメーターを例外ではなく破棄する。AWS が新しい課金の形を出したとき、ビルドが壊れるのではなく「わからない」に縮退すべきだからだ。

編集上の制約 (文字数、金額の禁止、確認日) は、**コミット済みデータに対するテストではなく `Service` のコンストラクタ**に置いてある。テストが捕まえられるのは既に書かれた不正なレコードだけで、コンストラクタはそれを構築不能にする。

「何が無料か」「どれが同じ課金の形か」「まだ未検証なのはどれくらいか」といった横断的な問いは `Catalogue` の担当で、ページテンプレートには置かない。「無料」の定義が1箇所にしかない状態を保つため。

### なぜ幾何計算を別モジュールにしたのか

`src/lib/diagram-layout.ts` が SVG 図解の裏にある計算を持っている。切り出したのは、境界マップが `height="-40"` のリングを出荷したから。型チェックは完全に通り、ブラウザでコンソールエラーを出し、**最内リング (その図の主役) を黙って消していた**。しかもテストを書いた結果、同じ欠陥が横軸にまだ残っていたことが判明した。

### なぜビルドガードがあるのか

`npm run build` は後段で 2 つのスクリプトを走らせる。

`scripts/csp-hashes.mjs` はビルド内の全インラインスクリプトをハッシュ化し、`dist/_headers` の `script-src` に書き込む。Astro は小さいスクリプトをファイルにせず埋め込むが、ポリシーは `script-src 'self'` なので、これが無いとブラウザが実行を拒否する。トップのカウンタは止まり、サービス一覧のフィルタは無反応になる。HTML は妥当なままで、ビルドも緑のままだ。ハッシュはコードが変われば変わるので貼り付けではなく生成しており、答えを `'unsafe-inline'` にしていないのもそのため。

続く `scripts/check-build.mjs` は、ビルド済み HTML から負の SVG 寸法と `NaN` 座標を探し、ロケール間でキーが揃っているかを検査し、全記事に確認日と最低 1 本の出典があることを要求し、上のポリシーから漏れたインラインスクリプトがあれば落とす。ユニットテストの下に敷いた二枚目の網で、コンポーネントが描画時に組み間違えたものを捕まえる。三枚目が `npm run test:smoke` で、ブラウザでしか見えないものを捕まえる。

## 鮮度の維持

ここにあるものが古くなるのは、こちらがコードを変えたからではない。AWS が変えたからだ。ページが廃止され、料率が動き、製品ラインごと改名されても、それを説明する URL は 200 を返し続ける。それを見つけるためのチェックが 2 つあり、聞いている質問が違う。

`scripts/check-sources.mjs` は、引用先のページがまだそこにあるかを聞く。リダイレクトを追い、ガイドの目次に着地したものは「消えた」と判定する。AWS がドキュメントを廃止するときは 404 ではなく、より曖昧な場所への 200 だからだ。

`scripts/check-freshness.mjs` は、誰かが最近見たかを聞く。全サービスレコードと全記事が `checked` 日付を持ち、90 日で警告、`--strict` を付ければ 180 日で失敗する。

どちらも push のたびに走る。そして `.github/workflows/claims.yml` で毎週も走る — 重要なのはこちらのほうで、定期実行の失敗には赤くする PR が無いため、`claims` ラベルで issue を立てる (既に開いていればコメントを足す)。

古いと言われたら、一次情報に当たり直してから日付を動かす。**読み直さずに日付だけ動かすと、この仕組みは検査ではなく儀式になる。**

## サービスの追加

`src/data/services/` の該当ファイルにオブジェクトを足すだけ:

```json
{
  "slug": "example",
  "name": "AWS Example",
  "category": "compute",
  "meters": ["time", "bytes"],
  "oneLiner": "読者が持ち帰れる1文。",
  "trap": "このサービスで一番よく間違えられる点。",
  "billOn": ["ExampleUsage-Hours"],
  "confidence": "high",
  "sources": ["https://aws.amazon.com/example/pricing/"],
  "checked": "2026-08-04"
}
```

`meters` は旧称 `egress` / `calls` を `bytes` / `units` の別名として受け付ける (リポジトリが変換する)。古い名前で書かれた調査結果もそのまま取り込める。slug の衝突と正規化不能はビルドが落ちる。本文が長すぎる、空、金額が入っている、AWS の出典が無い、確認日が不正 — これらは `Service` のコンストラクタが拒否する。**通らない**のではなく**作れない**。

調査バッチの取り込みには `node scripts/merge-services.mjs batch.json` を使う。slug がカテゴリを跨いで重複しないよう検出しながら、正しいファイルに振り分ける。

## ロケールの追加

`src/i18n/strings.ts` の `LANGS` に足し、文字列バンドルを埋め、`src/pages/<lang>/` を作る。ロケール一覧は他に3箇所ある — `astro.config.mjs` の sitemap 設定、`scripts/check-build.mjs` の `LANGS`、`src/layouts/Base.astro` の `og:locale`。全ロケールが同じキー集合を持つことはテストが保証する。片方の言語にしか存在しないページは、404 へのリンクではなく言語スイッチャー上でグレーアウトする。
